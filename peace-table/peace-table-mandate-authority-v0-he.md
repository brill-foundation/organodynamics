## 0. מעמד המסמך — לקרוא לפני הכול

עדי הכריעה בשאלה החוקתית שב-§14: היא בחרה באפשרות 3 (תיקון חוקתי מפורש), ותיקון זה אומץ כ-[`foundation/garnet-first-table-v0.3-he.md`](foundation/garnet-first-table-v0.3-he.md) §9.1. מסמך זה עצמו נשאר **Proposed** לגבי כל מנגנון תפעולי שהוא מתאר (סכימת המנדט, שני המעברים, השוואה, פישור, attestation, Shadow Mode, פריטי הפעולה) — אימוץ §9.1 קובע רק שמנדט אנושי מאושר, כמוגדר במסמך היסוד עצמו, **יכול** למלא את דרישת "אישור אנושי מפורש"; הוא אינו מאשר את המנגנון הספציפי שמסמך זה מציע, ואינו הופך אותו בעצמו לחוקה או למדיניות מאושרת. כל תוכן כאן שמניח ביצוע מואצל חי (Tier ≥2, ר' §10) נשאר **חסום בפועל** עד שגם: (א) פרטי המנגנון התפעולי יוכרעו במפורש כרשומת `Decided` נפרדת ב-Decision Register (PTDR-02, PTDR-09 ותלויותיהן), וגם (ב) קריטריון היציאה של Shadow Mode (§15) יתמלא. עד אז, שום קוד, prompt או ממשק אינו רשאי לממש Tier ≥2 כעובדה קבועה (בהתאם לאינווריאנט "אין ברירת מחדל שקטה", Decision Register §1). Tier 3 חסום **תמיד**, ללא תלות בכל הכרעה עתידית, בכל מצב.

## 1. ההקשר ורצון המפעילה

עדי מסרה בשיחת המפעילה עם Codex, ונשמרה כהקשר מחייב לבנייה:

> "אני חושבת שאולי כדאי להעביר למודלים יותר סמכויות, שפועלות בהתאם לרצון האנושי העולה בשולחנות איכשהו."

> "אולי נוסיף שלב שלפני שהמחלוקת חוזרת לשולחן, המודלים מנסים לייצר החלטה שהם מסכימים עליה?"

> "יופי. המשך"

שלוש ההנחיות האלה הן הבסיס העובדתי היחיד למסמך: (1) סמכות מואצלת נגזרת מרצון אנושי שעולה בשולחנות, לא מכוח עצמאי של מודל — ומכאן ש**השער האנושי חייב להיות על המנדט עצמו (הענקה/חידוש/הרחבה/ביטול), לא בהכרח על כל מופע ביצוע בודד**, אחרת הרצון האנושי שכבר בא לידי ביטוי בהענקת המנדט לא באמת "פועל" (ר' §10); (2) סבב פישור **אחד**, **חסום**, לפני החזרה לשולחן, שרשאי לגעת גם במחלוקת עובדתית הניתנת לבדיקה מול lineage משותף, לא רק בניסוח (ר' §8); (3) אישור להמשיך בניסוח תחת ה-slice הרגיל הנוכחי — אינו הכרעת PTDR ואינו תיקון חוקתי.

## 2. לגיטימציה אנושית מול סמכות מבצעית מואצלת

- **לגיטימציה** (הזכות לקבוע מה השולחן רוצה) נשארת תמיד ורק אנושית: יסוד §2.11 "מודלים הם משתתפים מסייעים, לא בעלי כוח פוליטי"; §2.10 "אין אדם, מודל או יו״ר במרכז."
- **סמכות מבצעית מואצלת** היא הרשאה מוגבלת-scope, מוגבלת-זמן, הפיכה, לבצע מחלקת פעולות מוגדרת מראש בתוך מנדט מאושר — היא **אינה** מקנה הצבעה, משקל, או מעמד קבוע (יסוד §9, §11).
- **הסכמה בין שני מודלים היא אות אמינות הנדסי בלבד — לעולם לא קונצנזוס אנושי, לא אמת, ולא תחליף להכרעת שולחן, ולא "אישור" במובן החוקתי.** נקודה זו חוזרת בכל סעיף רלוונטי במסמך זה (במיוחד §9).

## 3. אובייקט המנדט (Mandate record) — סכימה גרסאית מוצעת

```ts
interface Mandate {
  mandate_id: string
  version: number                 // גרסה, בדומה ל-policy_version (ארכיטקטורה §7)
  table_scope: string[]           // רשימת table_id-ים; [] = ללא היקף כלל — מנדט עם table_scope ריק אינו מעניק שום דבר עד שהיקף נקבע במפורש
  action_class: string[]          // allow-list: כל ערך חייב להופיע במדיניות מתוחזקת בנפרד (§ להלן), לא סכימה קבועה
  risk_tier: 0 | 1 | 2      // Tier 3 לעולם אינו חלק ממנדט (ר' §10, §16); לא ניתן להצמיד את הערך 3 לשדה זה בשום מופע
  permitted_discretion: string[]
  forbidden_discretion: string[]
  granted_by: string               // Actor.id אנושי מוסמך (עדי, או תפקיד לפי PTDR-10/PTDR-02 משוכלל)
  granted_at: string                // ISO-8601, נדרש בפועל — לא ינוחש
  expires_at: string                 // חובה; מנדט ללא תפוגה אינו קביל
  revocable: true                    // קבוע true; אין מנדט בלתי-הפיך
  reconciliation_policy: 'one_bounded_round'
  attestation_requirements: 'dual_independent'
  status: 'draft' | 'active' | 'revoked' | 'expired' | 'superseded'
  supersedes?: string               // mandate_id קודם, בדומה ל-knowledge_revision.supersedes
}
```

`action_class` אינו מוגבל תמידית לרשימת ארכיטקטורה §11.1: הוא allow-list שמאומת מול מדיניות `policy_version` מתוחזקת בנפרד (ארכיטקטורה §7), כדי שהסכימה עצמה תוכל לתמוך בעתיד בסמכות מואצלת שאושרה חוקתית מבלי לדרוש עיצוב מחדש. **נכון להיום, רשימת המדיניות עצמה מכילה אך ורק ערכי Tier 0/1** (ארכיטקטורה §11.1) — הוספת ערך ראשון מ-Tier 2 לרשימת המדיניות דורשת כעת (לאחר שהתנאי הסף החוקתי הוסר על ידי יסוד §9.1, ר' §14.1) רשומת `Decided` נפרדת של PTDR-02 (ותלויותיה) וקריטריון היציאה של Shadow Mode (§15) שהתמלא בפועל — לא רק את קיומו של תיקון §9.1 כשלעצמו. מנדט הוא רוויזיה גרסאית לכל דבר: שינוי עקרוני יוצר `mandate_id` חדש עם `supersedes`, לא עריכה דורסת (יסוד §2.14).

## 4. מותר ואסור בשיקול דעת מודל בתוך מנדט

**מותר** (בכפוף למנדט תקף ובתוך ה-`action_class` המוגדר):
- לדייק ניסוח, סדר, פורמט או רמת פירוט של פלט שכבר בתחום architecture §11.1.
- לבחור בין ניסוחים חלופיים שאינם משנים עובדה מהותית או תוצאה.
- בתוך מנדט Tier-2 חי (לאחר שגם התנאי הסף החוקתי הוסר על ידי יסוד §9.1 (ר' §14.1), וגם רשומת PTDR-02 הרלוונטית הוכרעה כ-`Decided`, וגם קריטריון היציאה של Shadow Mode (§15) התמלא בפועל): לבצע את מחלקת הפעולה המתוחמת שאושרה במפורש ברשימת המדיניות, בתוך `table_scope` ו-`expires_at` שלה.
- לסמן אי-ודאות, פער מקורות או צורך בהכרעה אנושית — תמיד מותר, ואף מחויב.

**אסור, גם בתוך מנדט תקף:**
- להרחיב `table_scope` או `action_class` מעבר למוגדר (scope creep).
- לבצע כל פעולה מרשימת Tier 3 (§10) — **בלי יוצא מן הכלל**, ללא תלות בקיום מנדט, לעולם.
- לדרוס או להחליש התנגדות מהותית שסומנה על ידי אדם.
- להאריך, לחדש או להרחיב מנדט באופן עצמאי — רק Actor אנושי מוסמך.
- להכריע שהמנדט עצמו חל כאשר יש עמימות בפרשנותו (ר' §7) — עמימות פרשנות מנדט תמיד עוצרת ועולה לאדם.

## 5. שני מעברים עיוורים מול סבב Proposer/Auditor — שני שלבים נפרדים

**שלב א' — שני מעברים עיוורים ובלתי תלויים:** Model A ו-Model B מקבלים אותו קלט (מנדט + snapshot מקורות) ומייצרים כל אחד פלט מלא **בלי לראות** את פלט האחר. אין תפקיד Proposer/Auditor בשלב הזה — שני המודלים שווים ועצמאיים לחלוטין.

**שלב ב' — סבב הפישור (§8), רק אם נדרש:** מופעל רק כאשר ההשוואה הסמנטית (§6) מגלה אי-התאמה. בשלב הזה, ורק בו, מתחלפים תפקידי Proposer/Auditor בין ריצות עוקבות: אחד המודלים (Proposer של הריצה) מציע מועמד פישור יחיד; המודל השני (Auditor) בודק את המועמד מול המגבלות הנוקשות של §8 ומאשר/דוחה אותו. הרוטציה מקבילה לרוטציית Builder/Reviewer ב-AGENTS.md §1, ומתועדת, כדי לצמצם anchoring bias.

## 6. השוואה סמנטית מובנית, לא זהות טקסטואלית

השוואה אינה diff על טקסט חופשי. כל פלט מפורק ל-claims אטומיים (בדומה ל-`lineage_edge`, architecture §6.4), וכל claim מ-A מושווה ל-claim מקביל מ-B בשלוש תוצאות אפשריות: **תואם סמנטית** (ניסוח שונה, משמעות זהה), **סותר**, **קיים באחד וחסר בשני**. תוצר ההשוואה הוא דוח מובנה, לא ציון יחיד — עקבי עם יסוד §12 "מפת מחלוקת מדויקת עדיפה על החלטת 51%".

## 7. סיווג מחלוקת (Disagreement taxonomy)

| סוג | הגדרה | טיפול בסבב הפישור (§8) |
|---|---|---|
| פרוצדורלית | ניסוח/פורמט/סדר, אין מחלוקת מהותית | ניתנת לפישור |
| עובדתית | claim הניתן לבדיקה מול lineage/ראיות משותפות | ניתנת לפישור **רק** אם ה-lineage מכריע חד-משמעית; אחרת נשארת פתוחה |
| נורמטיבית/מהותית | שיפוט ערך, סיכון או פגיעה | לעולם אינה מפוישרת על ידי המודלים; חוזרת לאדם גם אם נראית "קטנה" |
| פרשנות מנדט | עמימות בהיקף המנדט עצמו | תמיד חוסמת; מטופלת כ"אין בסיס לפעולה", לא כניחוש לטובת ביצוע |

## 8. סבב פישור אחד, חסום, עם שימור בלתי-הפיך של הפלטים המקוריים

- הפלטים המקוריים של A ו-B (טרם פישור) נשמרים **ללא שינוי וללא מחיקה** — רוויזיה נעולה, נגישה ל-audit.
- מותר סבב פישור **אחד בלבד**. בתוכו:
  - מותר ליישב מחלוקת **פרוצדורלית** (ניסוח/סדר/פורמט).
  - מותר ליישב מחלוקת **עובדתית**, אך ורק על ידי בדיקה משותפת מול lineage/ראיות משותפות (§6); אם ה-lineage תומך בבירור בטענה אחת, המועמד מאמץ אותה; אם ה-lineage אינו חד-משמעי, המחלוקת נשארת פתוחה ואינה "מפוישרת".
- **אסור בכל תנאי**, גם כלפי מחלוקת עובדתית: למצע בין שתי הערכות סותרות ללא הכרעת lineage (למשל ממוצע ציוני סיכון); למחוק או לרכך התנגדות מהותית שעלתה באחד הפלטים; להכריע מחלוקת נורמטיבית/מהותית (ערך, סיכון, trade-off) בשם בני אדם; לנחש פרשנות מנדט עמומה כדי "לאפשר" פעולה.
- מבנה הסבב: ה-Proposer (§5) מציע מועמד פישור יחיד; ה-Auditor בודק אותו מול הרשימה הנוקשת שלעיל ומאשר/דוחה. אם נדחה — אין ניסיון שני.
- אם לאחר הסבב עדיין קיימת מחלוקת: מוחזרת לשולחן **מפת מחלוקת קומפקטית** + **שאלה אנושית ממוקדת אחת**. לא מוחזר "ניסיון שני" ולא "פשרה".

## 9. אישור כפול עצמאי (dual attestation) — אות אמינות לביצוע, לא מקור לגיטימציה

- לאחר (אם היה) סבב הפישור, כל מודל **חותם בנפרד** על הפלט הסופי: נימוק, רמת ביטחון, וקישור ל-claims שהוא בפרט תומך/מסתייג מהם. **אין הצהרה משותפת יחידה.**
- **בשום מקרה אין להוסיף מודל שלישי כמכריע אוטומטי**; מחלוקת שלא פוחתה חוזרת לאדם — לעולם לא ל"רוב" מלאכותי של שלושה מודלים.
- **attestation כפול הוא בקרת אמינות הנדסית לביצוע בתוך מנדט שכבר אושר אנושית — הוא אינו, ולעולם לא יהיה, מקור הלגיטימציה, הנוכחות הפוליטית, או "האישור" עצמו.** ה"אישור" היחיד בעל משקל חוקתי הוא הענקת/חידוש/הרחבת המנדט על ידי אדם מוסמך (§10) — לא הסכמת שני המודלים אחריו.
- הבחנה זו פותרת מתח לכאורה: attestation כפול **כן** מפעיל בפועל ביצוע Tier-2 בתוך מנדט פעיל (§10) — אך ורק לאחר שגם התנאי הסף החוקתי הוסר על ידי יסוד §9.1 (ר' §14.1), וגם רשומת PTDR-02 הרלוונטית הוכרעה כ-`Decided`, וגם קריטריון היציאה של Shadow Mode (§15) התמלא בפועל — כלומר המודלים "מאשרים" במובן טכני-פנימי שהפלט המשותף שלהם עומד בתנאי הסף להרצה. זה שונה מהותית מלהיות "מאשר" במובן החוקתי של יסוד §9/PTDR-02 (הענקת סמכות, קביעת scope, הכרעת materiality) — תפקיד שנשאר אנושי בלעדי תמיד. attestation אינו מקנה למודל מעמד "מאשר" פוליטי; הוא שער טכני-הנדסי בתוך מרחב שכבר תוחם ואושר על ידי אדם.

## 10. שכבות סיכון ושערי מנדט אנושיים

השער האנושי הוא **על המנדט**, לא בהכרח על כל מופע ביצוע בודד:

- כל הפעלה, חידוש, הרחבה או ביטול של מנדט היא שער אנושי טרי בפני עצמו: פעולה מפורשת, קשורה לגרסת מנדט ספציפית (`mandate_id`+`version`), לא "אישור עקרוני" גורף (מקביל ל-AGENTS.md §4.2 "current operator turn" ול-§5 fail-closed).
- כל עוד מנדט נמצא ב-`status: active`, פעולות Tier-2 שנמצאות ברשימת ה-`action_class` שלו רשאיות — **רק** לאחר שגם (א) התנאי הסף החוקתי הוסר על ידי יסוד §9.1 (ר' §14.1), וגם (ב) רשומת PTDR-02 הרלוונטית הוכרעה כ-`Decided`, וגם (ג) קריטריון היציאה של Shadow Mode (§15) התמלא בפועל (עודן חסומות כליל עד שכל שלושת התנאים מתקיימים) — לרוץ דרך צינור שני-המודלים + השוואה + פישור + attestation כפול **בלי שער אנושי נפרד לכל מופע בודד**. זהו המימוש הישיר של הנחיה 1 של עדי (§1): הסמכות המבצעית פועלת בהתאם לרצון האנושי שכבר בא לידי ביטוי בהענקת/חידוש המנדט, ולא ממתינה לאישור נקודתי חוזר על כל פעולה.
- Tier 3 (לא-מואצל לעולם) דורש שער אנושי טרי, ספציפי לפעולה, **תמיד** — גם כאשר קיים מנדט פעיל רחב. שום מנדט, בשום גרסה, אינו יכול לכסות Tier 3.

| Tier | תיאור | דוגמאות | שער |
|---|---|---|---|
| 0 | קריאה/תצפית בלבד, אין פלט מפרסם | — | קיים כבר, ללא שינוי |
| 1 | ניסוח/הצעה בתחום ארכיטקטורה §11.1 | סיכום, Mirror draft, clustering, הצעת Sketch/Challenge/split-merge | מותר כבר היום, ללא שער נוסף |
| 2 | ביצוע מואצל, מתוחם והפיך, בתוך מנדט פעיל | split/merge מתוחם יחיד (ארכיטקטורה §9.3, הפיך); מעבר בשלות PENCIL→INK מתוחם; הפעלת Reality Test שההשערה/מדדים שלו כבר ננעלו ע"י אדם | שער על המנדט (הענקה/חידוש/הרחבה) — **חסום כליל בפועל עד שרשומת PTDR-02 הרלוונטית הוכרעה כ-`Decided` וקריטריון היציאה של Shadow Mode (§15) התמלא בפועל (התנאי הסף החוקתי עצמו כבר הוסר על ידי יסוד §9.1, ר' §14.1)** |
| 3 | לא-מואצל לעולם, ללא תלות במנדט | הצבעה/משקל פוליטי; הכרעת materiality; הסתרה/ענישה/מחיקת קול; העברת אדם בין שולחנות; PRESS/BROADCAST; אישור Decision סופי או פרשנות תוצאת Reality Test | שער אנושי טרי לכל מופע, תמיד, ללא יוצא מן הכלל |

**הצדקת השיוך:** הפעולות ב-Tier 3 הן אלה שבהן טעות שקטה יוצרת נזק בלתי-הפיך או גוזלת **לגיטימציה** אנושית, לא רק ביצוע — הצבעה/משקל, materiality, השתקת קול ומעבר אדם מנוסחות כך במפורש ביסוד §2.5, §2.11, §9. לרשימה זו מתווספות כאן **PRESS/BROADCAST ואישור Decision/פרשנות תוצאת Reality Test** מאותו נימוק בדיוק: הן יוצרות הסתמכות חיצונית או נועלות תוצאה כ"מה שהשולחן החליט" — הפעולה עצמה היא לגיטימציה, לא רק ביצוע, ולכן נשארת אנושית תמיד, גם בהנחת מנדט עתידי רחב ומאושר חוקתית. לעומת זאת, split/merge מתוחם, מעבר בשלות PENCIL→INK מתוחם והפעלת Reality Test שכבר ננעל אנושית הם מועמדים אפשריים ל-Tier 2 כי הם הפיכים (ר' ארכיטקטורה §9.3 לדפוס rollback) ואינם, כשלעצמם, קובעים לגיטימציה — הם מבצעים משהו שאדם כבר תיחם.

**הערה לעקביות סכימה:** הטבלה שלעיל ממשיכה לתאר את כל ארבע השכבות (0–3) לצורך הנמקת המדיניות בכללותה, אך שדה `Mandate.risk_tier` בפועל (§3) מוגבל ל-`0 | 1 | 2` בלבד. Tier 3 אינו ניתן לקידוד כערך מנדט תקף בשום מופע ובשום גרסה — הוא נשאר תמיד מחוץ לאובייקט המנדט עצמו, לא רק "חסום בפועל" בתוכו.

## 11. ביטול, rollback, lineage ו-audit

- ביטול מנדט הוא מיידי; פעולה שהחלה לפני הביטול אך טרם הושלמה נעצרת.
- כל תוצר מנדט נושא lineage מלא: `mandate_id`+גרסה, שני הפלטים המקוריים, דוח ההשוואה, פלט הפישור (אם היה), שתי חתימות ה-attestation.
- audit הוא append-only ואינו ניתן לעריכה (architecture §12), כולל ניסיונות פעולה שנחסמו.
- rollback של פעולה שבוצעה תחת מנדט יוצר אירוע נגדי ששומר את הניסיון, ולא מוחק אותו (architecture §9.3 pattern).

## 12. הסתייגות גיוון ספקים (provider diversity)

"בלתי תלויים" משמעו המלצה חזקה לשני ספקי מודל/משפחות שונות, כדי לצמצם שגיאה מתואמת. אם בפועל שני המעברים מגיעים מאותו ספק/משפחת מודל, יש לסמן זאת **במפורש** כאות אמינות חלש יותר — לא להציג כשקול לעצמאות אמיתית.

## 13. צימוד לפרטיות ולעלות — PTDR-07 / PTDR-08

- כל ריצה, לרבות Shadow Mode, כפופה למדיניות ה-redaction, ה-retention וההסכמה המוצעת ב-PTDR-07 (Open) במלואה; עצם היותה ללא השפעה על state אינו מתיר שליחת קלט אמיתי לפני שהשערים האלה הוסדרו או אושרו במפורש לריצה הספציפית.
- מנדט **אינו** יכול להעניק סוג-משימה שלא אושר תקציבית תחת PTDR-08 (Open); `action_class` בכל מנדט חייב להיות תת-קבוצה של מה שכבר תוקצב שם, ותת-קבוצה של רשימת המדיניות שב-§3.
- שתי הרשומות האלה נשארות Open; מנדט אינו עוקף אותן ואינו מחליט בשמן.

## 14. ניתוח חוקתי — המתח מול מסמך היסוד §9

**מסמך היסוד §9 קובע במפורש, וללא שינוי במסמך זה:** מודלים "רשאים להציע ולנסח בלבד"; ללא אישור אנושי מפורש הם אינם רשאים להעביר אדם בין שולחנות, להסתיר/להעניש/למחוק קול, להכריע שהתנגדות אינה מהותית, לאשר פיצול/איחוד, להעביר פריט ל-INK/PRESS/BROADCAST, לאשר Decision או Reality Test, או להצביע/לקבל משקל פוליטי. `architecture §6.1` מבטא זאת כאינווריאנט: "MODEL לעולם אינו עובר דרך נתיב API שמפרסם Decision, PRESS או BROADCAST ללא אישור אנושי מפורש."

מסמך זה **אינו** מתקן, מפרש מחדש בשקט, או עוקף את §9. שלוש האפשרויות הבאות מוצגות ניטרלית, ללא הכרעה:

1. **פרשנות מצמצמת:** "אישור אנושי מפורש" משמעו תמיד לחיצת אדם על מופע ספציפי; מנדט, יהיה מוגדר ומוגבל ככל שיהיה, לעולם אינו ממלא את הדרישה — גם לא ברמת המנדט (§10). **בטוח ביותר, לא דורש תיקון חוקתי, אך אינו מעניק "יותר סמכות" כפי שביקשה עדי בהנחיה 1 (§1)** — הוא משמר את המצב הקיים בפועל, כולל צורך באישור לכל מופע.
2. **פרשנות מרחיבה (ללא תיקון פורמלי):** אקט האישור/החידוש/ההרחבה של עדי למנדט מוגדר-scope, מוגבל-זמן, הפיך (§3, §10) — הוא עצמו "האישור האנושי המפורש" הנדרש עבור כל מופע Tier-2 שנופל בתוך אותו מנדט תקף, כל עוד כל ביצוע בפועל נשאר קפדני בתוך ה-scope ונושא lineage לאישור המנדט. **מרחיבה סמכות בפועל בדיוק כפי שביקשה עדי (שער על המנדט, לא על כל מופע), אך מותחת את המשמעות הפשוטה של "מפורש"** (עדי לא אישרה את המופע הספציפי, רק את המחלקה) — סותרת את רוח יסוד §2.14/§0 ("אין מחיקה שקטה של הדרך") אם מוצגת כפרשנות מובנת-מאליה ולא כהכרעה מודעת.
3. **תיקון חוקתי מפורש:** עדכון עתידי, נפרד, למסמך היסוד עצמו, שיגדיר במפורש שמנדט מאושר, בעל הקריטריונים שבמסמך זה, ממלא את "אישור אנושי מפורש" לפעולות Tier-2 בתוך scope. **הדרך הנקייה ביותר, אך היא תיקון חוקתי — מסמך זה, ו-Session Contract Issue #57 כולו, אינם מוסמכים לבצעה** (מסומן במפורש ב"גבולות אישור" של Issue #57).

המלצת הגרסה הקודמת של מסמך זה הייתה אפשרות 3 (תיקון חוקתי מפורש, ב-Session נפרד וממוקד), בדיוק משום שאפשרות 2 עלולה להיתפס כפרשנות שקטה מהסוג שהחוקה אוסרת. עדי אימצה המלצה זו — ר' §14.1.

### 14.1 הכרעת עדי — אפשרות 3 נבחרה (Issue #60)

עדי הכריעה במפורש באפשרות 3 בשיחת המפעילה עם Codex, ואישרה את חוזה הסשן שהוצע ב-Issue #60:

> מאשרת את אפשרות 3 ואת חוזה הסשן המוצע.

ההכרעה אומצה כתיקון חוקתי מצומצם ב-[`foundation/garnet-first-table-v0.3-he.md`](foundation/garnet-first-table-v0.3-he.md) §9.1: Mandate אנושי מאושר, גרסאי, מוגבל-scope, מוגבל-זמן והפיך ממלא את דרישת "אישור אנושי מפורש" של מסמך היסוד §9, אך **רק** עבור פעולות Tier-2 הפיכות בתוך ה-scope וחיי המנדט המדויקים, ו**רק** דרך שני מעברי מודל עיוורים, השוואה סמנטית, סבב פישור חסום יחיד ואישור כפול עצמאי — בדיוק כפי שתואר באפשרות 3 ובמנגנון §3–§13 של מסמך זה.

**מה בדיוק הוכרע ומה נשאר פתוח:**

- **הוכרע (חוקתי):** העיקרון שמנדט אנושי מאושר, כמוגדר במסמך היסוד עצמו, יכול למלא את דרישת "אישור אנושי מפורש" עבור Tier-2 הפיך בתוך scope וחיים מוגדרים. Tier 3 נשאר בלתי-ניתן-להאצלה לעולם, ללא יוצא מן הכלל.
- **נשאר Proposed (תפעולי, לא הוכרע):** סכימת המנדט המדויקת (§3), פרטי שני המעברים/ההשוואה/הפישור/attestation (§5–§9), רשימת Tier-2 המדויקת שתיכנס בפועל למדיניות (§10, §18 פריט 3), fixtures ומדדי Shadow Mode (§15), וכל עדכון בפועל ל-PTDR-02/PTDR-09 (Decision Register).
- **לא הוכרע ונשאר חסום:** הפעלה חיה בפועל של כל פעולת Tier-2 כלשהי; הרצת Shadow Mode על קלט אמיתי לפני הסדרת PTDR-07; ומיזוג כל PR עתידי שינסה לממש חלק מהמנגנון התפעולי.

**קביעה מפורשת, לא ניתנת לפרשנות:** אימוץ §9.1 במסמך היסוד **אינו**, כשלעצמו, מפעיל שום ביצוע מואצל חי (Tier ≥2 ב-§10) בקוד, במדיניות או בפרומפט. ביצוע כזה נשאר חסום עד שגם המנגנון התפעולי המדויק יוכרע כרשומת `Decided` נפרדת ב-Decision Register (PTDR-02, PTDR-09), וגם קריטריון היציאה של Shadow Mode (§15) יתמלא בפועל. Tier 3 חסום תמיד, ללא תלות בכל הכרעה. אין להסיק מהכרעת עדי באפשרות 3 אישור לשום דבר מעבר למה שרשום כ"הוכרע" לעיל — לא ל-PTDR-02, לא ל-PTDR-09, לא ל-Shadow Mode על קלט אמיתי, ולא למיזוג PR עתידי כלשהו.

## 15. Shadow Mode — fixtures, מדדים, קריטריון יציאה

לפני כל ביצוע חי (Tier ≥2): הרצה מלאה של הדגם המלא (שני מעברים + השוואה + פישור אם נדרש + attestation כפול) על fixtures, **ללא שום השפעה על state** (shadow בלבד). Shadow Mode עם **fixtures סינתטיים** מותר ומומלץ **כבר עכשיו**, ללא תלות בסטטוס `Open` הנוכחי של PTDR-02/PTDR-09 או בקריטריון היציאה שלהלן, מכיוון שהוא shadow בלבד ואינו מבצע Tier ≥2 בפועל. **שימוש בקלט אמיתי (מידע אמיתי מהשולחנות) ב-Shadow Mode חסום** עד שהוסדרו במפורש מדיניות ה-redaction, ה-retention וההסכמה במסגרת PTDR-07 (ר' גם §13), או עד אישור אנושי מפורש מתאים לריצה הספציפית; **PTDR-07 נשארת Open** ואינה מוכרעת על ידי מסמך זה.

**מדדים מוצעים:**
- שיעור הסכמה סמנטית לפני פישור.
- שיעור הצלחת פישור בתוך הסבב היחיד, מפוצל לפי סוג מחלוקת (§7): פרוצדורלית לעומת עובדתית-נפתרת-lineage.
- התפלגות סוגי מחלוקת (§7), כולל שיעור מקרי "פרשנות מנדט" חוסמת.
- שיעור מקרים שהוחזרו לשולחן עם שאלה אנושית.
- שיעור false-consensus שנמצא בדגימת audit אנושית (שני המודלים "הסכימו" אך טעו יחד).
- עלות ו-latency לכל מחזור (architecture §13).

**קריטריון יציאה מוצע (לא מוכרע):** מספר סבבי Shadow Mode עוקבים ללא חוסם מהותי, על פני fixtures הכוללים לפחות מיעוט מהותי ידוע מראש, מקרה false-consensus מכוון, ומקרה מחלוקת עובדתית עם lineage לא-חד-משמעי (כדי לוודא שהמערכת אכן מחזירה אותו לשולחן ולא "מפוישרת" אותו) — לפני שעדי אף שוקלת מעבר ל-Tier 2 חי.

## 16. מצבי כשל

- outage של ספק אחד באמצע מעבר כפול — אין להשלים עם מודל בודד ולהציג כ"עצמאי".
- ניסיון פישור לחרוג מגבולות §8 (מיצוע עובדות ללא lineage מכריע/מחיקת התנגדות/פשרת ערך/ניחוש פרשנות מנדט) — עצירה קשה, סימון כתקרית, לא רק "אי-הסכמה".
- זחילת scope שקטה של `action_class`/`table_scope` — נאסר במפורש; המנדט הוא allow-list, לא ניחוש.
- attestation "חותמת גומי" ללא חישוב עצמאי אמיתי — נבדק מדגמית ב-audit, כשל מוגדר מראש.
- עמימות פרשנות מנדט המטופלת בשקט כ"כן מותר" במקום כחוסמת — כשל מוגדר במפורש (§7).
- הענקת/חידוש מנדט המוצג כ"אישור עקרוני" גורף במקום שער טרי וספציפי (§10) — כשל מוגדר במפורש.
- ניסיון להצמיד `risk_tier: 3` (או כל פעולת Tier 3) לאובייקט מנדט — נדחה תמיד בשלב הוולידציה של הסכימה (§3); מתועד כ**רשומת audit בלבד** (§11), ולעולם אינו הופך למנדט תקף, לניסיון ביצוע, או לניסיון פישור לגיטימי.
- הרצת Shadow Mode על קלט אמיתי (ולא fixtures סינתטיים) לפני הסדרת PTDR-07 (redaction/retention/הסכמה) או קבלת אישור אנושי מפורש מתאים — כשל מוגדר במפורש; ריצה כזו **נעצרת**, לא רק מסומנת בדיעבד.

## 17. תוצאות (Consequences)

**בעד:** מסגרת מדידה (Shadow Mode) לפני כל דיון בביצוע חי; אינה טוענת סמכות שלא אושרה; שומרת lineage מלא; מפרידה לגיטימציה מביצוע; השער האנושי על המנדט (לא על כל מופע) מממש בפועל את הנחיית עדי §1 מבלי לדרוש תיקון חוקתי כדי *להגדיר* את הדגם — רק כדי *להפעילו*.

**נגד/סיכון:** מוסיפה מורכבות תפעולית (שני מודלים, השוואה סמנטית, attestation, ניהול מחזור חיים של מנדט) לפני שהוכח ש-Tier 1 הקיים אינו מספיק; יוצרת אשליית "ביצוע מואצל" גם כשבפועל Tier 2 חסום בכל מצב עד שרשומת PTDR-02 (ותלויותיה) הוכרעה כ-`Decided` וקריטריון היציאה של Shadow Mode (§15) התמלא בפועל, ו-Tier 3 חסום לצמיתות ללא יוצא מן הכלל — יש להימנע מהצגת המסמך הזה כאילו הוא כבר משנה את המצב בפועל, וכן מהצגת התיקון החוקתי (יסוד §9.1) כשלעצמו כאילו הוא מפעיל ביצוע חי כלשהו.

## 18. פריטי פעולה (כולם Proposed, ללא סמכות ביצוע)

1. **[הוכרע — עדי בחרה באפשרות 3, Issue #60; ר' §14.1 ויסוד §9.1]** התנאי הסף החוקתי הוסר. תנאי הסף הנותר לכל Tier ≥2 בכל צורה שהיא הוא כעת: (א) רשומת PTDR-02 (ותלויותיה) הוכרעה כ-`Decided`, וגם (ב) קריטריון היציאה של Shadow Mode (§15) התמלא בפועל.
2. **פתוח על גבי fixtures סינתטיים בלבד.** בניית fixtures סינתטיים והרצת Shadow Mode מלאה (§15) עליהם — כולל תרחישי Tier-2 מדומים ותרחישי מחלוקת עובדתית עם lineage לא-חד-משמעי — אינה מבצעת דבר ואינה חסומה על ידי שער ביצוע. **הרצה על מידע אמיתי של משתתפים או שולחנות אינה כלולה בכך ונשארת חסומה** בשערי הפרטיות של §15, עד לרשומת PTDR-07 `Decided` או אישור אנושי ספציפי. זהו הפריט היחיד ברשימה שניתן להתחיל בו היום, ורק בגבול הזה.
3. **חסום** עד שמתקיימים **כל** אלה: (א) רשומת PTDR-02 (ותלויותיה) הוכרעה כ-`Decided`; (ב) קריטריון היציאה של Shadow Mode (§15) התמלא בפועל; (ג) ניתן אישור מימוש נפרד ומפורש. רק אז: המחלקה הראשונה שתיכנס בפועל לרשימת המדיניות (`policy_version` allow-list, §3) היא **מחלקת ה-Tier-2 הקטנה וההפיכה ביותר** הזמינה (למשל split/merge מתוחם יחיד) — **לא Tier 1**, שכבר מותר היום ואינו דורש את המנגנון הזה כלל. בכל מקרה, המחלקה חייבת לעמוד בתנאי הכשירות המצטברים של יסוד §9.1 סעיף 2, ולא להימנות ברשימת Tier 3 שביסוד §9.1 סעיף 4.
4. **חסום** עד שרשומת PTDR-02 הוכרעה כ-`Decided`: הגדרת סכימת `mandate` בפועל במודל הנתונים (ארכיטקטורה §7), כשלב נפרד ובעל אישור מימוש משלו. `risk_tier` נשאר מוגבל ל-`0 | 1 | 2` בלבד; Tier 3 אינו ניתן לקידוד כערך מנדט תקף בשום מופע (§10, ויסוד §9.1 סעיף 4).
